Chapter 13

Conclusion

What this package shows, what it doesn't, and what remains to be tested.

13.1 The wall doesn't go away — it changes shape

The idea running through this whole document is simple enough to state once more, plainly, as a closing point rather than an opening one: adding a memory tier to a KV-cache system does not eliminate the memory wall that decode-heavy inference runs into. It relocates it. Before a tier exists, the wall is a capacity wall — a context grows, the cache grows with it, and eventually there is nowhere left to put it. A tier relieves that problem directly; that part is not in question. What replaces it is not nothing. HBM-side bandwidth on the host is unchanged by the presence of a tier — on the one platform we measured end to end, a DGX Spark GB10, sustained bandwidth topped out at 236.5 GB/s, 87% of the platform's rated spec, regardless of whether a tier sits behind it. And two problems appear that did not exist before: how fast data can cross into the tier, and how much latency each individual transfer costs. Those are not restatements of the capacity problem. They are new, independent constraints, and a design that only reasons about capacity will walk straight into them. Four constraints, not one, is the frame this package has argued for throughout — capacity, HBM bandwidth, tier-ingress bandwidth, and per-transfer latency — and restating it here, for the last time, is deliberate: it is the actual intellectual contribution of the document, more than any single number in it.

13.2 What is actually being claimed

It is worth being precise about this in a conclusion, because it is easy to overstate. The eviction-scoring method used throughout — a decayed-frequency, exponential-moving-average score — is not new work. It is LRFU, published by Lee et al. at SIGMETRICS in 1999, and it is credited as such here again, plainly, without hedging. The contribution this package makes is not an algorithm. It is a protocol-level claim: that eviction-policy metadata, keyed to block identity, should be treated as a migratable object that persists across tier boundaries rather than something that resets when a block moves. The evidence for that claim is a simulated result — provisional, and described as such throughout — showing a 34.15 percentage-point hit-rate improvement for LFU under a 32 GiB HBM budget when metadata persists across a tier boundary versus when it resets. That number carries a useful property: it doesn't require any CXL hardware to test, because the question it answers is about what state a controller chooses to preserve, not about the physical characteristics of the tier the state lives on. That distinction is why the claim can be made with more confidence than anything else in the package that depends on hardware we did not have.

13.3 What this package is, and is not

Said directly: this is a hardware-measured decomposition of decode-phase bandwidth into weight and KV components, taken on one real platform, paired with a corrected simulation of how eviction policies behave under tier-crossing conditions. That is a real, bounded contribution. It is not a validated CXL memory-tier system. No CXL device was in the loop at any point — the tiering behavior is simulated, not measured on the interconnect it is meant to describe. And the persistent-metadata result, despite being the strongest piece of evidence in the package, is still a simulation result, and it is provisional for a specific, disclosed reason: an earlier revision of this work contained a simulation defect that inverted four of five headline findings, and that history is part of why every number here is labeled by how it was produced rather than presented as settled fact.

13.4 What's still open

A short list of what would need to happen before any of this graduates from provisional to validated. First, fp8 KV-cache measurement: compression changes the byte cost of every transfer, and it's an open question whether it changes the ratio between weight and KV bandwidth demand or just scales both proportionally. Second, repeating the bandwidth decomposition on a mixture-of-experts model, where the weight-access pattern is structurally different from the dense models measured here. Third, testing the persistent-metadata result against real workload traces instead of the synthetic Zipfian, scan, and loop access patterns used in this round of simulation — synthetic patterns are useful for isolating a mechanism, but they are not a substitute for production traffic. And fourth, the one item on this list that actually requires physical CXL hardware rather than more simulation: confirming that policy metadata survives a real eviction and re-admission round trip on an actual device, not just in a model of one.

13.5 A note on what "done well" means here

There isn't a bigger claim to reach for at the end of this. Work like this is done well when it states what it found plainly, tags every number by the kind of evidence that produced it — measured on real hardware, simulated and provisional, or borrowed from prior published work — and lets the findings that don't hold up be dropped rather than defended. That was the discipline this revision tried to hold to, after an earlier one didn't. It is not a dramatic note to end on, and it isn't meant to be. It's just the one that leaves the fewest debts for whoever picks this work up next.
